# キッチンモニター要件・コメント確認サマリー

- 作成日: 2026-07-22
- 情報源: [Google ドキュメント「キッチンモニター要件まとめ」](https://docs.google.com/document/d/1bYGWy1GT_aodLE2CjbMHJ_vhK5d9xfcWpvz4FNExZb4)
- 対象: Google ドキュメントの本文3タブとコメント20件
- この文書の目的: 要件メモ・現行仕様・コメントの確認状況を分け、次のレビューで決める順序を明確にする
- 更新境界: Google Drive側の本文、コメント、共有設定は変更していない

## 1. 先に見るべき結論

Google ドキュメントには、現行仕様、将来案、他製品から得たアイデア、API上の懸念が混在している。したがって、記載内容をそのまま「決定済み要件」として実装へ渡すことはできない。

コメントは20件中16件が未解決である。解決済みの4件も、結論の返信ではなく解決操作だけが残っているため、仕様決定済みとは判断しない。

現行のVueモックは、注文別／テーブル別表示、時間警告、完了・取消、部門表示、並び替え・ピン留めの操作確認には使える。一方で、他端末同期、注文取消、注文方法、実データの取得可否、履歴・分析、テイクアウト、スヌーズなどは未決またはモック範囲外である。

## 2. 情報源の位置付け

| タブ | 内容 | このサマリーでの扱い |
| --- | --- | --- |
| `要件整理` | 現在は空 | 決定済み要件と未決事項の整理先として使える |
| `メモ` | Airレジ、LBB、funfoなども参照した要望・アイデア | 仮説・検討材料。決定済みとは扱わない |
| `今のキッチンモニター仕様` | 現行アプリの注文一覧、履歴、設定画面のメモ | 既存挙動の確認材料。実装前には現行コード・画面で再確認する |

モック上で実際に確認できる挙動は、別途 [現行モック機能仕様](./current-mock-functional-spec.md) を正本とする。

## 3. 本文から読み取れる要件のまとまり

### 一覧で確認・処理すること

- 注文単位とテーブル単位を切り替え、注文数・テーブル数・経過時間を把握する。
- 経過時間や目標調理時間で優先度を判断する。
- 商品、コース、オプション、お好み、メモ、数量を確認し、調理済み数を処理する。
- 同一商品や合計量を一覧で把握するトータルビューを検討する。
- 表示対象をカテゴリや調理場ごとに絞り込む。

### 状態変化・運用

- 完了後に取り消せる猶予を設けてから、一覧から非表示にする。
- 注文取消、数量変更、配膳済み、呼び出しをどう見せるかを決める。
- 他端末での処理を反映し、調理場が異なる端末間でも状態を共有する。
- 新規注文、遅延、取消への通知音と、音量・ミュートを設定する。

### 設定・将来検討

- 文字サイズ、表示密度、列数、表示名、色、時間しきい値、カテゴリ・テーブルの対象範囲を設定する。
- スヌーズ、履歴、分析、テイクアウト、モバイルオーダー・引換券モニターとの関係を検討する。

## 4. コメントによる確認状況

### 集計

| 状態 | 件数 | 扱い |
| --- | ---: | --- |
| 未解決 | 16 | 次のレビューで回答または決定が必要 |
| 解決済み | 4 | 解決操作だけで結論本文がない。決定内容を再記録する必要がある |

### 未解決の確認事項

| 分類 | 確認事項 | コメントが示す論点 | 次に必要な確認 |
| --- | --- | --- | --- |
| 表示データ | カテゴリー名・注文番号・トッピング・注文方法 | 現行にない表示項目や、Figmaとの差分がある | 表示項目の一覧と情報源を確定する |
| スヌーズ | 利用目的と手動追加機能 | 意図が不明で、現行の手動追加UIも未確認 | だれが、何を、いつ再表示したいかを業務シナリオで決める |
| 設定UI | 色の選択 | 文字色との組合せを考慮した候補制にしたい | 自由色か、アクセシビリティを満たす候補色かを決める |
| テーブル・注文 | `1テーブル2注文` | 表示上限なのか、表示単位の説明なのか不明 | 実際の最大表示件数と、あふれた場合の扱いを決める |
| API・同期 | Waiterの注文取得APIに必要項目がない可能性 | メニュー同期・Webhook追従が必要になる可能性 | 必要項目、取得元、同期方式、初期リリース範囲を確認する |
| 商品表示 | トッピング、標準／簡易コース、プラン、お好み | 現行を含めた表示パターンが未確認 | 実データ例ごとの表示ルールを作る |
| 分析 | 保存期間 | 現行の注文データは7日後に消える | 分析に必要な保持期間と保存責任を決める |
| 数量変更 | 同じ商品を一部だけ処理する場合 | 現行は変更前後の数量も示す | 増減だけでよいか、変更履歴・差分表示が必要かを決める |
| キャンセル | 明細単位の取消 | 注文全体だけでなく明細取消の挙動が不明 | 表示、確認、消去、復元、他端末反映を決める |
| メモ | 明細メモの位置 | 明細単位でメモが付く可能性がある | 一覧・詳細のどちらに何を表示するかを決める |
| 注文方法 | ハンディ／モバイルオーダーの判定 | 判定方法が不明 | API・Webhookで取得できる識別子を確認する |
| 注文ID | 店舗利用者へ見せる意味 | ULIDを表示する利用場面が不明 | 利用者価値がなければ非表示候補とする |
| テーブル結合 | 結合時のテーブル名 | 現行はカンマ区切り | 結合テーブルの識別・並び・ピン留めの扱いを決める |
| テーブルカテゴリ | 取得・同期コスト | 店舗詳細を個別取得して同期する必要があり、優先度を下げたい | 初期リリースに含めるか、代替のグループ軸にするかを決める |
| レイアウト | 長い注文の扱い | 縦スクロールか、複数列へ分割するか。余白のしきい値も必要 | 現場に比較モックを見せ、読みやすさと誤操作で選ぶ |

### 解決済み表示だが、結論を再記録すべき事項

次のコメントはGoogle Docs上で解決済みになっている。ただし返信本文はなく、解決操作だけが記録されている。

| 論点 | コメント上の確認内容 | 次に残すべき決定 |
| --- | --- | --- |
| 通知設定 | `音色`・`通知音`の意味 | 通知の種類、発火条件、音の設定項目 |
| 注意時間 | キッチンモニター側の設定項目か | 設定する主体と保存単位 |
| 完了後の表示 | 消えるか、グレーアウトか | 状態、取消方法、表示継続時間 |
| 一括調理済み | 現行のプログレスバーに相当するか | 取消猶予中の見せ方と操作 |

## 5. 次のレビューで決める順序

### 優先1: 実データと同期の前提

1. 注文方法、カテゴリ、テーブルカテゴリ、メモ、取消、数量変更に必要なデータは取得できるか。
2. 他端末の調理・取消をどのイベントで反映するか。
3. 初期リリースで同期・保存が必要な状態と、端末内だけでよい状態を分ける。

### 優先2: 現場操作の基本ルール

1. 完了・取消・明細取消・数量変更の状態遷移。
2. 注文／テーブル／商品のどの単位を一覧から消すか。
3. スヌーズを初期リリースに含めるか。

### 優先3: 一覧の見せ方

1. 注文別・テーブル別の利用場面と基本レイアウト。
2. 長い注文・複数注文・結合テーブルの見せ方。
3. 一覧に常時出す項目と、詳細へ移す項目。

### 優先4: 設定・拡張機能

通知、色、文字サイズ、履歴、分析、テイクアウトは、上記の基本ルールとデータ前提が決まってから扱う。

## 6. モックとの連携方法

1. このサマリーの未解決事項から、次回レビューで扱う論点を3件以内に選ぶ。
2. 比較が必要な論点だけ、Vueモックで操作できる案を用意する。
3. レビューで `採用`、`変更`、`保留`、`対象外` を決める。
4. 決まった業務ルールをGoogle Docsの `要件整理` と [現行モック機能仕様](./current-mock-functional-spec.md) の両方へ、役割に応じて反映する。

Google Docsは業務上の決定と確認履歴、モック機能仕様は実際に触れる挙動を管理する。どちらにも同じ詳細を二重に書かない。
